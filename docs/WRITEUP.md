# Writeup

**Matching approach.** I treat the Bellhaven website as the source of truth and match on address first, because a sale or rebrand changes a facility's name but not its building. The scraper crawls the whole site rather than trusting the directory: the directory lists 34 communities, while the homepage says 35 and links the 35th only from a "new this year" notice. Candidates come in three tiers: street + ZIP, then street + city (which caught a ZIP typo), then an exact name in the same city (which caught a placeholder PO Box). A matching name in another city is never a match, which avoided a same-named facility in Colorado. I keep every candidate, so duplicates surface. The survivor is chosen rule by rule (billing history, correct parent, name, address formatting), and the card shows which rule decided. When only soft rules decided, the proposal is marked low confidence for the reviewer. The CHOW SOP is a separate rule from matching: an exact match still checks revenue AND AR before any re-parent. Accounts no longer on the website are flagged Needs Review rather than moved or inactivated. Nothing writes without approval. Decisions are fingerprinted so reruns don't re-propose them, creates use client-side idempotency keys, and every write is re-checked beforehand and read back afterwards.

**How I used AI tools.** I built this with Claude Code: exploring the API and data, designing the pipeline, writing code and tests, and drafting docs. I directed the scope, reviewed the UI as the reviewer, and made every approve and reject decision myself. I used Cursor Agent (Grok) for a narrow second-opinion review of the CHOW and re-run logic. It found two real re-run bugs, which I verified and fixed with tests; I rejected one of its claims after checking it. A separate Claude session served as a tutor, so I could learn concepts without cluttering the build session. No LLM runs inside the pipeline; matching is deterministic and explainable.

**What I'd build next.** Address standardization or geocoding; corroborating ownership from external sources such as state licensing and CMS ownership data; letting the reviewer pick a different survivor; shared storage for the ledger with reviewer identity, so the scheduler and the reviewers see the same decisions; and alerts on stale or failed proposals.
