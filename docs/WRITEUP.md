# Writeup

**Matching approach.** The website is the source of truth, and I match on address first: a sale renames a facility but doesn't move the building. The scraper crawls the whole site, because the directory lists 34 communities while the homepage says 35 and links the 35th only from a notice. Candidates come in tiers: street + ZIP, then street + city (caught a ZIP typo), then exact name in the same city (caught a PO Box). The same name in another city never matches. Keeping every candidate surfaces duplicates. The survivor is chosen rule by rule (billing history, correct parent, name, formatting), the card shows the deciding rule, and soft-only decisions are flagged low confidence. CHOW applies after matching: every re-parent first checks revenue AND AR. Accounts missing from the website are flagged Needs Review, not moved. Nothing writes without approval. Decisions are fingerprinted so reruns don't repeat them, creates use idempotency keys, and every write is re-checked and read back.

**How I used AI tools.** Claude Code helped me explore the API, design the pipeline, and write code, tests and docs. Cursor Agent (Grok) gave a narrow second review of the CHOW and rerun logic and found two real bugs, which I verified and fixed with tests; I rejected one of its claims. A separate Claude session tutored me on concepts. I set the scope and made every review decision. As the reviewer, I reshaped the UI: short titles, a single CHOW table, the kept copy on duplicate cards, ⚖️ on the deciding row, and ✏️/gray instead of a verbose source column. I rejected a proposal that would overwrite a PO Box billing address with the physical one, and chose not to roll back data to stage the demo. No LLM runs in the pipeline; matching is deterministic and explainable.

**What I'd build next.** Address standardization or geocoding; ownership evidence from external sources (state licensing, CMS); letting the reviewer pick a different survivor; a shared ledger with reviewer identity; and alerts on stale or failed proposals.
